# Deployer GitHub SSH key generation — design

Date: 2026-08-11
Status: Approved

## Problem

`08-laravel-deployment.sh` clones a repository over SSH (`--repo git@...`) as the
`deployer` user, but nothing in this repo provisions an SSH keypair for `deployer`
to authenticate outbound to GitHub with. Today an operator has to generate and
register that key by hand outside of these scripts.

## Goal

`01-packages-deployer.sh` — the script that actually creates the `deployer` user
(per `AGENTS.md`; `05-folder-structure.sh` only assumes the user already exists) —
should also generate an SSH keypair for `deployer` and print the public key so the
operator can paste it into GitHub (as a repo Deploy Key or under a machine
account).

## Design

Add a new section to `01-packages-deployer.sh`, appended after the existing SSH
access / passwordless-sudo-verification section. `DEPLOYER_USER`, `DEPLOYER_HOME`,
`DEPLOYER_GROUP`, and `SSH_DIR` are already in scope there.

1. Target file: `${SSH_DIR}/id_ed25519` — `deployer`'s default SSH identity file.
   No `~/.ssh/config` changes and no dedicated non-default filename; the key is
   used as-is by any outbound SSH connection `deployer` makes, including the
   `git clone git@github.com:...` step in `08-laravel-deployment.sh`.
2. If a keypair already exists at that path, print a warning to stderr that it is
   about to be replaced and that any repository trusting the old key will lose
   access until the new public key is added to GitHub, then remove the old
   `id_ed25519` / `id_ed25519.pub`.
3. Generate a fresh `ed25519` keypair as the `deployer` user directly (`sudo -u
   deployer ssh-keygen -t ed25519 -f "${SSH_DIR}/id_ed25519" -N "" -C
   "deployer@<hostname>"`) so file ownership is correct from creation with no
   separate `chown` needed. Empty passphrase (`-N ""`) is required because
   `deploy.sh` (generated by `08-laravel-deployment.sh`) runs unattended with no
   human present to unlock a passphrase-protected key.
4. Print the resulting public key to stdout with an explicit instruction to add
   it to GitHub.

### Rerun behavior (deliberate deviation)

Every run of `01-packages-deployer.sh` regenerates this keypair unconditionally
— it does not converge/skip like the rest of this repo's idempotent scripts.
This is an explicit choice: simplicity of "always fresh key" was preferred over
skip-if-exists safety. The tradeoff is real — rerunning this script (e.g. to
re-verify provisioning, or because a future edit adds an unrelated package)
silently invalidates GitHub access for any release until the operator notices
and re-pastes the new public key into GitHub. The stderr warning in step 2 is
the mitigation: it fires every time an existing key is about to be destroyed.

### Explicitly out of scope

- Populating `~/.ssh/known_hosts` for `github.com` (host-key trust for the
  actual `git clone` is a concern for `08-laravel-deployment.sh`/`deploy.sh`,
  not this script).
- Any `~/.ssh/config` host-alias wiring — the key is generated at the default
  identity path and used implicitly.
- Registering the key with GitHub via API — this remains a manual step the
  operator performs by pasting the printed public key.

## Testing

- `bash -n debian13-laravel-postgresql/01-packages-deployer.sh`
- `shellcheck debian13-laravel-postgresql/01-packages-deployer.sh`
- Manual run on a disposable Debian 13 host: verify keypair is created with
  correct ownership (`deployer:deployer`) and permissions (600 private / 644
  public), verify the public key prints, verify a second run overwrites the
  key and prints the warning first.
